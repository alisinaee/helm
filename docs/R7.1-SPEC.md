# R7.1 — Start from the GUI wakes an open session

Gap (GAP-ANALYSIS section 2): GUI Start only adds an entry to `queue.json`. If no Claude session is open, nothing visible happens.

## What already exists (do not rebuild)
- `roadmap/services/notify.py`: an osascript notification with a 60 s rate limit and a `notify:false` switch. `queue.enqueue` already calls it with "Start X queued. Open a Claude session in P or run: roadmap watch".
- `roadmap/commands/watch.py`: `wait()` long-polls `queue.json` and `questions.json` and prints `start P2.4` / `stop` / `answer` / `timeout`.
- `roadmap/services/hooks.py`: `_session_start` and `_stop_pickup` surface queued tasks (with rules, a cap of 3).
- `web/js/views/details.js` `queueHtml`: shows "Queued to start" whether or not a session is there.

So the wake path works only when a session is open or the user sees the notification. What is missing: **the board does not know whether a session is listening**, so the GUI cannot say "waiting for a session" or offer the next step.

## Chosen mechanism
1. **Session presence file** `presence-<hash>.json` in the state dir (never in the repo; `<hash>` is the first 16 hex digits of the SHA-256 of the data dir path), holding: `{"hook": iso, "watch": iso|null, "watchPid": int|null}`.
   - Every hook event writes `hook` at most once per 30 s (an mtime check first, so it stays inside the 300 ms hook budget).
   - `watch.wait()` writes `watch`=now and `watchPid` when it starts, refreshes `watch` every 30 s while polling, and clears both when it exits (`try/finally`).
2. **Derived state** in the snapshot: `session = "watching"` (the watch stamp is under 60 s old), `"open"` (the hook stamp is under 10 min old), else `"none"`.
3. **GUI**: the Run section word becomes:
   - queued + watching → "Queued, a session is picking it up"
   - queued + open → "Queued, picked up at the session's next stop"
   - queued + none → "Queued, waiting for a session", plus a **Copy command** button that copies `cd <path> && claude "roadmap watch"`. A text-only fallback is used when the clipboard is unavailable.
4. **Notification text** (queue.enqueue): when presence is `none`, the body becomes "Start X queued; no session open. Run: cd <path> && claude". Otherwise it keeps today's text. Still rate-limited.
5. **Optional launch** (off by default, config `launchOnStart: true` per project): after enqueue, when presence is `none`, run `osascript -e 'tell app "Terminal" to do script "cd <quoted path> && claude"'` once per 10 min. The path is shell-quoted with `shlex.quote` and then AppleScript-escaped. Never under unittest; a no-op off macOS. Nothing is launched without the opt-in, because opening an interactive `claude` session spends tokens.

Why not more: a resident daemon that runs `claude -p` would spend tokens without the user knowing and conflicts with the STOP rule. Presence plus one copyable command closes the "nothing visible" gap at about zero token cost.

## Tests
- `tests/unit/test_presence.py` (new): throttle (2 touches in 30 s = 1 write); the 60 s / 10 min edges of state; a corrupt file reads as `none`; never raises.
- `tests/unit/test_watch.py`: with a fake clock, watch stamps are written at the start and refreshed, and cleared after a timeout and after an event.
- `tests/unit/test_hooks.py`: a SessionStart fixture writes `hook`; the timing assertion of under 300 ms still passes.
- `tests/unit/test_launcher.py` (new): off by default; with the config on and presence `none`, the runner gets an argv list containing a quoted path with spaces and quotes; a second call within 10 min does nothing; presence `open` means no launch.
- `tests/unit/test_notify.py`: the enqueue body depends on presence (injected runner).
- `tests/web/test_panel.py` or `test_work.py`: the three Run words and the Copy button appear only for `none`.
- Run: `python3 -m unittest discover -s tests -t . -q`, `make check`, `make check-ui`.

## Token cost
- Build: about 30k in total (6 Haiku tasks of about 4–6k each, plus a head review of about 6k).
- Runtime: 0 tokens for presence and notification. `roadmap watch` costs one tool call per wake. The opt-in launch costs one session start (the user chose it).

## Risks
- **Hook latency** (WP22 area): the write is throttled by mtime and stays under 1 ms in the common case; the test guards the 300 ms limit.
- **Stale presence** after a crash: `watch` is only trusted for 60 s and `hook` for 10 min, so a dead session decays to `none`.
- **Launch injection**: the path comes from the config, never from the request; argv only, with shlex and AppleScript escaping; opt-in.
- **Git noise**: none. The presence file lives in the state dir, outside the repo, so it needs no ignore entry.
- macOS Automation permission prompt on the first launch: document it in the config help.
