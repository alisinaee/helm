# WP27: usage ledger and limit rows

- `roadmap/services/ledger.py` (new): `state/ledger.json`, 14 local days, at most 4 KB, atomic and locked.
  `record_reading` (weekly points: `w - lastW` when `w >= lastW`, else `w`; the first reading of a day is compared with
  the last reading before midnight; the first reading ever adds nothing), `record_spend` (K per project per day),
  `rate` (points per thousand tokens over 7 days, none under 200k tracked), `estimate`, `pace_per_hour` (last 2 hours).
  A corrupt file is moved to `ledger.json.corrupt` and started again.
- `roadmap/services/limits.py` (new): the row model `{id, scope, window, kind, value, action}`. Stores: global rows in
  config `limits`; project rows in budget `limitRows`; read-through AUTO (autonomy `stopAtPercent`, kind acct) and BUD
  (budget project total, kind tok). `check_spec`, `write_row`, `remove_row`, `evaluate_rows` (ok, warn at 80%, block
  at 100% for action block, unknown never blocks; stale usage over 30 minutes or a missing or corrupt ledger makes
  pct and acct unknown; any failure is ok and logged once a minute), `evaluate`, `meters`, `status_line`, `show_lines`.
- `roadmap/services/usage.py`: a weekly reading is recorded in the ledger on every sync and push (best effort);
  recompute now fans out with `control.recompute_all`.
- `roadmap/services/budget.py`: `record_job_spend` adds the tokens to the ledger for the project that owns the folder;
  `update`, `set_project_limit` (action warn stored as budget `limitAction`); `limitRows` in the document.
- `roadmap/services/control.py`: `_evaluate` takes the block and warn lines from `limits.evaluate_rows` (the old weekly
  and project budget checks are gone; their messages are kept). Block scope is `global` when only global rows block.
  `recompute_all` (every project, so a global block reaches every sentinel), `after_write` fans out, `set_limit_row`
  and `remove_limit_row` (agent guard, activity line, recompute). The state gains `day`.
- `roadmap/services/cmdops.py`: `limit.set` takes the legacy `{pct}` or `{scope, window, kind, value, action, id?}`;
  its undo restores the prior row (or removes a new one). `limit.rm {id}` is new, its undo sets the row back. Both
  are in LOOSENING (refused from phone) and under the agent guard.
- `roadmap/commands/limits.py`: `limit set [PCT]` (legacy, unchanged output), `limit set --scope --window --pct N |
  --tokens K [--warn]` (prints `L3 set`), `limit rm ID`, `limit show` (at most 8 lines). `limit budget` unchanged.
- `roadmap/commands/status.py`: one `limits:` line after `budget:`, within the 8-line and 700-character budget.
- `roadmap/commands/job.py`: `job done --tokens` recomputes control after the spend (a job is a trigger).
- `roadmap/core/snapshot.py` and `roadmap/services/loader.py`: `meters` (`limits`, `today`, `week`), added only when
  given, so the golden snapshot is unchanged.
- `roadmap/store/config.py`: `update_limits` (locked read-modify-write of the global rows).
- Tests: `tests/unit/test_wp27_limits.py` (34 tests: ledger derivation, 200k minimum and estimate, pace, the kind and
  window and action matrix, stale and corrupt fail-open, global fan-out, hook deny and override, the byte-identical
  autonomy-only project, agent refusal, undo, the CLI, `status`, job spend, meters). Existing tests were adjusted
  where the rule changed: `tests/unit/test_control_support.py` writes a fresh `updated` stamp and a ledger reading
  (`set_usage`), and `tests/unit/test_commands_service.py` lists `limit.rm` among the public ops.
- Docs: `docs/API.md` (meters, cmd ops), `docs/ARCHITECTURE.md` (ledger and limits services, on-disk additions).

## Deviations
- Project rows are stored under budget key `limitRows`, not `limits`: budget.json already has `limits` (an object of
  caps), so a list under the same key was not possible.
- The autonomy stop with no `stopAtPercent` is no longer enforced as 100% by default: the AUTO row exists only when
  `stopAtPercent` is set. Before WP27 a missing value meant 100 whenever a weekly reading existed.
- `ledger.json` also keeps `recent` (readings of the last two hours, at most 36) for the pace projection.
- The day rollover is handled by evaluating with the current date at every recompute (the usage loop recomputes every
  reading, about every two minutes); no separate timer was added.

## Gaps
- The 5-hour window, per-model calibration and the history chart are LATER (as the spec says).
- A corrupt ledger is moved aside silently except for one log line; nothing in the UI reports it yet.
- The hook fast path reads only the sentinel, so a block from yesterday stays until the next recompute (usage loop,
  job, or limit change) runs.
